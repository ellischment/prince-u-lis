### Основная кнопка: кремовая вместо оранжевой (по заказчику, 12 августа 2026)

**Найден системный подвох кэша, он шире курсов.** Сборка упала на пререндере `/kursy` с «`startDate.getTime is not a function`». Причина: `cachedRead` построен на `unstable_cache`, а тот сериализует результат в JSON, поэтому при попадании в кэш поля `Date` приезжают **строками**, хотя тип обещает `Date`. Пока значение просто выводят на страницу, подвох незаметен, и потому он дожил до сегодня: курсы — первый код, который по дате считает. Проявляется только при пререндере: на первом живом рендере данные ещё не прошли через кэш и остаются настоящими `Date`, поэтому ручная проверка в браузере его не показывает.

Починено восстановлением дат сразу после чтения (`reviveRuns` в lib/courses.ts). Предупреждение записано в `lib/cache.ts` рядом с `cachedRead`, то есть там, где на него наткнётся следующий, а не только здесь. Кто дальше будет читать даты через кэш (расписание, события, статьи), обязан делать то же самое.

Отдельно про тесты, честно: мои 14 тестов этого не поймали и не могли — они проверяют чистые функции на настоящих `Date`, а баг живёт на границе с кэшем. Поймала сборка. Это довод в пользу того, что `next build` в `npm run check` стоит раньше сквозных тестов, а не вместо них. Общее правило на будущие шаги: где появляется вычисление над данными из кэша, там проверкой чистых функций не обойтись, нужен прогон через реальную сборку. Модульные тесты не ловят стыки с инфраструктурой (кэш, сериализация, пререндер) — это не упрёк тестам, а карта того, кто что ловит.

**Технический долг, не блокирующий, но настоящий: починить узел, а не только предупредить о нём.** Сейчас в `lib/cache.ts` стоит предупреждение, а даты чинит каждый вызывающий у себя (`reviveRuns` в lib/courses.ts). Это заплатка вниманием, а такие живут до первого невнимательного. Настоящая починка: `cachedRead` сам возвращает даты датами — ревайвер при чтении из кэша, либо честная типизация «наружу приходят строки» с приведением в одном месте. Пока не сделано, расписание и события наступят на те же грабли, несмотря на комментарий. Делать отдельной задачей, не попутно.

**Изоляция, а не переопределение.** Имена переменных у сайта и панели совпадают, а значения почти все разные (`--deep` сайт `#0C1A2E` / панель `#101E39`, `--r` `20px` / `14px`, и так далее). Переопределить сайтовые переменные в `:root` значит покрасить сайт в панельные цвета. Вместо этого палитра панели объявлена в `app/admin/admin.module.css` на обёртке `.theme` (`display: contents`, так что раскладка не меняется), подключённой через новый `app/admin/layout.tsx` — он оборачивает и вход, и саму панель, общего layout над `/admin` раньше не было. Переменные наследуются по дереву документа, поэтому общий компонент (Button, Card), попав внутрь `/admin`, автоматически получает панельные значения, не будучи переписанным.

Проверено числами на боевой сборке, не на глаз: `getComputedStyle` на `:root` отдаёт сайтовые значения (`--deep: #0c1a2e`, `--r: 20px`, `--ok` пусто), внутри `/admin` — панельные (`--deep: #101e39`, `--r: 14px`, `--ok: #5fbf8a`). Сайт при этом не сдвинулся: фон главной, радиус карточки занятия и цвет кнопки «Записаться» после правки такие же, как были.

**Найдена и починена течь холста.** `body` лежит снаружи обёртки `.theme` (React не может обернуть сам `<body>` без отдельного root-layout на каждую ветку), поэтому при резиновой прокрутке за край видна была полоса сайтового `--deep`, а не панельного. Правило `body:has(.theme) { background: #101e39 }` — значение записано числом, а не `var(--deep)`, потому что на `body` эта переменная всё равно разрешится в сайтовую.

**Список занятий переведён на настоящую таблицу** (`components/admin/Panel.tsx`: `Panel`, `Table`, `Badge`) по словарю компонентов макета — было `<ul>` с грид-вёрсткой. У макета для узких экранов решения для таблиц нет вовсе (только сайдбар складывается), а Definition of Done требует 320px без горизонтальной прокрутки страницы. Решение: таблица прокручивается внутри своей обёртки (`overflow-x`), обёртка с `tabIndex={0}` и `aria-label`, страница не едет. Проверено на 320px: прокрутки страницы нет, таблица (624px) листается внутри блока (288px). Заголовки столбцов со `scope="col"`.

Переведён только список занятий — это было нужно, чтобы проверить палитру и словарь на живом разделе. Остальные разделы панели (расписание, отзывы и так далее) по-прежнему на старой вёрстке, переводятся по мере того, как до них доходит очередь по PLAN.md, не одним махом сейчас.

Известный узел на будущее: браузерные процессы на портах разработки (3000, 3100) иногда не освобождаются между сессиями — проверка отвечала не тому серверу, замечено по логу при работе над курсами. Проверять только на сервере, чей PID/порт видно в своём логе запуска.

### Схема авторизации amoCRM переведена на долгосрочный токен (документация, кода ещё нет)

Задача вне очереди шага 2.1, только документная правка: код интеграции amoCRM ещё не написан (шаг 0.4 отложен, ждёт доступа студии), поэтому исправление источников правды до появления кода дешевле, чем правка после.

Решение: amoCRM выпускает долгосрочный токен прямо в настройках интеграции (без обмена кода авторизации на access/refresh пару). `AMO_REFRESH_TOKEN`, `AMO_CLIENT_ID`, `AMO_CLIENT_SECRET` убраны как артефакты OAuth2-обмена, в рантайме долгосрочного токена не участвуют. `AMO_ACCESS_TOKEN` оставлен как есть (переименование не стоило правок по всем документам): в нём теперь лежит долгосрочный токен как есть, используется как Bearer. `AMO_PIPELINE_ID` не тронут, к схеме авторизации не относится.

Правки: SPEC.md р.14 (токен долгосрочный, автообновление не требуется), ARCHITECTURE.md р.10 (строка «Обновление токена amoCRM» убрана из таблицы фоновых задач — с долгосрочным токеном такой задачи не существует), PLAN.md шаг 10.1 (требование OAuth2 заменено на долгосрочный токен) и шаг 11.2 (пункт «Ежедневное обновление токена amoCRM» убран), `.env.example` и `../SETUP.md` (шесть/пять строк AMO_* сокращены до трёх/двух: AMO_SUBDOMAIN, AMO_ACCESS_TOKEN, [AMO_PIPELINE_ID]).

`npm run check` зелёный после правок (код не менялся, только документы).
