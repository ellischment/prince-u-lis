# ARCHITECTURE. Как всё устроено внутри

Техническая часть. Отвечает на вопрос «что происходит между нажатием кнопки в панели и обновлением страницы у гостя». Читается агентом вместе со `SPEC.md`.

---

## 1. Общая схема

```
Гость (браузер)
   │  GET страницы
   ▼
Next.js сервер ──► кэш страницы ──► если нет в кэше, читает из базы ──► рендерит HTML
   │
   │  POST формы (заявка)
   ▼
Обработчик заявки ──► валидация ──► запись в базу ──► текстовый журнал
                                          │
                                          ├──► amoCRM (с повторами)
                                          └──► Telegram

Администратор (браузер)
   │  действие в панели
   ▼
Серверное действие ──► проверка роли ──► валидация ──► запись в базу
                                                │
                                                ├──► сброс кэша затронутых страниц
                                                └──► запись в журнал действий
```

Ключевая связка, ради которой существует этот документ: **любая запись в базу из панели обязана сбросить кэш тех страниц, которые от неё зависят.** Без этого гость будет видеть старую версию до перезапуска сервера.

## 2. База данных: решение и условия

### Что выбрано

SQLite через Prisma. Файл базы лежит на диске сервера в примонтированном томе.

### Почему это оправдано для этого проекта

| Критерий | Значение здесь | Вывод |
|---|---|---|
| Одновременные записи | Единицы в час: заявки гостей и правки администратора | Блокировка записи не проблема |
| Чтения | Сотни в день, все кэшируются | База почти не нагружается |
| Число серверов | Один | Общая база не нужна |
| Кто обслуживает | Один человек без администратора баз | Простота решает |
| Резервная копия | Обязательна по договору | Копирование одного файла |

### Обязательные условия, без которых решение перестаёт быть безопасным

1. **Режим WAL.** Включается один раз: `PRAGMA journal_mode = WAL`. Позволяет читать во время записи. Без него редкая запись будет блокировать выдачу страниц.
2. **Никакого специфичного для SQLite SQL.** Все обращения только через Prisma. Ни одного сырого запроса, кроме `PRAGMA` при старте.
3. **Ограничения SQLite учтены в схеме.** SQLite через Prisma не поддерживает перечисления и массивы. Поэтому:
   - статусы хранятся строкой, допустимые значения заданы константами в коде и проверяются валидацией
   - списки (например, время в открытом дне) хранятся строкой в формате JSON
   - это уже отражено в модели данных `SPEC.md` раздел 2
4. **Резервная копия делается корректно.** Не копированием файла на живой базе, а командой `sqlite3 dev.db ".backup backup.db"`. Простое копирование во время записи даёт битый файл.
5. **Файл базы вне репозитория и вне образа контейнера.** Только том, иначе обновление приложения сотрёт данные.

### Когда придётся перейти на PostgreSQL

Переход нужен, если случится хотя бы одно:

- сайт переезжает на несколько серверов или в автомасштабирование
- появляется вторая система, которая пишет в ту же базу
- одновременных записей становится больше нескольких в секунду
- нужен полнотекстовый поиск по русской морфологии

Что для этого понадобится: сменить `provider` в `schema.prisma`, пересоздать миграции, перенести данные скриптом. Работы примерно на день при условии, что правило про отсутствие специфичного SQL соблюдалось.

**Вывод.** Начинаем на SQLite осознанно, а не потому что проще. Условия выше обязательны и проверяются на приёмке.

Список того, что ломается при переносе в контейнер. Проверяется на этапе 0.5.

| Что | Настройка |
|---|---|

| Миграции | `prisma migrate deploy` при старте контейнера, не при сборке |

| Размер загрузки | Ограничение и в приложении, и на обратном прокси |

## 3. Рендеринг и кэш: как правка доезжает до гостя

Самая частая ошибка в таких проектах: панель пишет в базу, а сайт продолжает показывать старое. Ниже точная схема.

### Режим рендеринга по страницам

| Страница | Режим | Тег кэша |
|---|---|---|
| Главная | Статическая с тегами | `home`, `lessons`, `masters`, `works`, `events`, `articles`, `reviews`, `schedule`, `texts` |
| Все занятия, страница занятия | Статическая с тегами | `lessons`, `categories` |
| Расписание | Динамическая, без кэша | нет |
| Команда, страница мастера | Статическая | `masters`, `lessons` |
| Каталог, страница товара | Статическая | `works`, `shop`, `categories` |
| Праздники, страница формата | Статическая | `celebrations` |
| Сотрудничество | Статическая | `partnerships` |
| Бонусы | Статическая | `bonus` |
| Блог, страница статьи | Статическая | `articles` |
| События | Статическая | `events` |
| Вопросы, политика | Статическая | `texts` |
| Панель `/admin/*` | Динамическая, без кэша | нет |

Расписание сделано динамическим намеренно: оно зависит от текущего дня недели, и кэш здесь дал бы открытый вторник в среду.

### Карта сброса кэша

После каждой записи в панели вызывается сброс по тегам. Точное соответствие:

| Действие в панели | Что сбросить |
|---|---|
| Занятие: создание, правка, скрытие | `lessons`, плюс путь `/zanyatiya/[slug]` |
| Категория или фильтр | `categories`, `lessons`, `works`, `shop` |
| Мастер | `masters`, плюс `/komanda/[slug]` |
| Работа | `works`, плюс `/kupit/[slug]` |
| Товар-услуга | `shop`, плюс `/kupit/[slug]` |
| Формат праздника | `celebrations`, плюс `/otprazdnovat/[slug]` |
| Вид сотрудничества | `partnerships` |
| Уровень бонусов | `bonus` |
| Статья: публикация, правка, снятие | `articles`, плюс `/blog/[slug]`, плюс `sitemap.xml` |
| Событие | `events` |
| Отзыв | `reviews` |
| Сетка расписания, часы, открытые дни | `schedule` |
| Тексты и оформление | `texts`, `home` |
| Медиа: загрузка, удаление | тег той сущности, к которой привязано |

**Правило для агента.** Каждое серверное действие панели заканчивается вызовом сброса кэша. Действие без сброса считается незавершённым и не проходит проверку.

### Как это проверяется

Ручной тест, который выполняется после каждого раздела панели:

1. Открыть страницу сайта в одной вкладке
2. В другой вкладке изменить данные в панели и сохранить
3. Обновить первую вкладку полностью: изменение видно
4. Повторить, но вместо обновления перейти на эту страницу по внутренней ссылке из другого раздела: изменение тоже видно

Второй сценарий обязателен. В браузере есть свой кэш переходов, и страница может браться из него, даже когда серверный кэш уже сброшен. Страницы, которые обязаны быть всегда свежими, помечаются динамическими.

### Адрес курса: одна каноничная страница

Курс это `Lesson` с форматом «Курсы» (SPEC.md р. 9a), то есть та же запись, что
и занятие. Без правила она открывалась бы по двум адресам сразу, а это дубль
в выдаче. Правило:

- Каноничный адрес курса `/kursy/[slug]`. Только он в карте сайта, только он в
  `generateStaticParams` своего маршрута, self-canonical на себя
- `/zanyatiya/[slug]` для занятия с форматом «Курсы» отдаёт **постоянный
  редирект** на `/kursy/[slug]`. Код именно **308**, а не 301: `permanentRedirect`
  в Next отдаёт 308, поисковики трактуют его так же, как 301. В документе стоит
  308, потому что это фактическое поведение, проверенное запросом. Формат
  проверяется на момент запроса, а не хранится в таблице `Redirect`: у той своя
  работа, переименование адреса. Иначе смена формата в панели оставила бы
  редирект висеть на старом месте
- `/kursy/[slug]` для занятия любого другого формата отдаёт **404**, а не
  встречный редирект назад. Это не забытая ветка, а защита: два встречных
  постоянных редиректа на изменяемом поле дают вечную петлю у всех, кто
  закэшировал первый (308 и 301 кэшируются жёстко), как только студия сменит
  формат. 404 петлю обрывает, и поломка видна сразу, а не через месяц в поддержке
- Ссылки на занятие строятся через `lessonHref` из `lib/courses.ts`, а не
  подставляются строкой: карточка курса ведёт сразу на `/kursy`, без прохода
  через редирект

## 5. Валидация

Одна схема на поле, используется и на клиенте, и на сервере. Клиентская проверка нужна для удобства, серверная для безопасности. Клиентскую можно обойти, серверную нельзя.

Обязательные правила:

| Поле | Правило |
|---|---|
| Имя | 2–80 символов, обрезка пробелов |
| Телефон | приведение к формату +7XXXXXXXXXX, проверка длины |
| Комментарий | до 1000 символов |
| Согласие | обязательно `true`, иначе отказ |
| Занятие | либо существующий идентификатор, либо пустое значение «пока выбираю» |
| Дата и время | только из числа открытых, произвольный текст в отдельном поле |
| Markdown статьи | очистка от исполняемого кода перед сохранением и при выводе |
| Загружаемый файл | тип определяется по содержимому, размер до 10 МБ, только изображения |
| Ссылка на видео | только домены VK Видео, Rutube, YouTube |

Ошибка валидации возвращает список полей и понятные тексты, форма не очищается.

## 6. Доступ и роли

- Вход по почте и паролю, пароль через bcrypt
- Сессия в httpOnly cookie, срок 14 дней, привязка к идентификатору сессии в базе
- Промежуточный обработчик защищает всё `/admin` кроме страницы входа
- Проверка роли выполняется **на сервере в каждом действии**, а не только скрытием пунктов меню
- Блокировка на час после 5 неудачных попыток с одного адреса
- Владелец может завершить все сессии одним действием

| Раздел | admin | owner | tech |
|---|---|---|---|
| Содержимое и расписание | да | да | да |
| Журнал заявок | да | да | да |
| Настройки и доступы | нет | да | да |
| Журнал действий | нет | да | да |
| Система и безопасность | нет | да | да |

## 7. Операции панели

Все операции реализуются серверными действиями. Общий контракт каждой операции:

1. Проверить сессию и роль
2. Проверить входные данные схемой
3. Выполнить запись в транзакции
4. Записать строку в журнал действий
5. Сбросить кэш по карте раздела 3
6. Вернуть результат или понятную ошибку

Набор операций по сущностям одинаковый: создать, изменить, скрыть или показать, изменить порядок, удалить с подтверждением. Дополнительно:

| Сущность | Особые операции |
|---|---|
| Занятие | пересчёт готовности страницы, привязка медиа, теги задач анкеты |
| Статья | закрепить (снимает закрепление у прежней), опубликовать, снять с сайта, предпросмотр |
| Отзыв | отметить согласие, публикация блокируется без отметки для фото и видео |
| Категория | создать подкатегорию, сменить тип отображения (только у первого уровня) |
| Расписание | скопировать часы на всю неделю, предупреждение при выходе за часы работы |
| Медиа | загрузка с обработкой, изменение порядка, отвязка |
| Заявки | выгрузка журнала за месяц, повторная отправка в amoCRM |
| Telegram | тестовое уведомление, проверка связи |

## 8. Конвейер заявки

Порядок строгий, менять нельзя.

```
1. Приём POST на /api/requests
2. Проверка частоты: не более 5 заявок с адреса за 10 минут
3. Валидация схемой
4. Проверка дублей: тот же телефон и тип за последние 10 минут
5. Шифрование имени и телефона
6. Запись в таблицу Request со статусом pending
7. Дозапись строки в текстовый журнал месяца, телефон в маскированном виде
8. Ответ гостю: успех. Дальнейшее происходит в фоне
9. Попытка отправки в amoCRM
      успех  -> статус sent, сохранение идентификатора сделки
      ошибка -> статус failed, счётчик попыток
10. Отправка уведомления в Telegram со ссылкой на сделку
```

Шаги 6 и 7 обязаны выполниться до шага 9. Гость получает подтверждение независимо от доступности внешних систем.

Повторы: через 1, 5, 15, 60 минут, максимум 5 попыток. Выполняет фоновая задача. После исчерпания попыток заявка остаётся в статусе failed и подсвечивается в панели.

## 9. Медиа

```
Загрузка -> проверка типа по содержимому -> проверка размера
   -> sharp: приведение к webp, создание версий 400, 800, 1600 пикселей
   -> сохранение в /uploads/{год}/{месяц}/
   -> запись в таблицу Media с размерами и весом
   -> привязка к сущности
```

Оригинал сохраняется отдельно на случай перегенерации. Удаление медиа удаляет и файлы, и запись, но только после подтверждения. Видео файлами не загружается, хранится только ссылка.

## 10. Фоновые задачи

Выполняются по расписанию через системный планировщик, который дёргает защищённый адрес `/api/cron` с секретным ключом.

| Задача | Когда | Что делает |
|---|---|---|
| Повторы заявок | каждые 5 минут | берёт заявки со статусом failed и не исчерпанными попытками |
| Резервная копия | ежедневно в 04:00 | база через `.backup`, папка uploads архивом, хранение 30 копий |
| Проверка восстановления | раз в месяц | разворачивает последнюю копию в отдельный файл и проверяет целостность |
| Архив событий | ежедневно | события с прошедшей датой помечаются прошедшими |

## 11. Ошибки и наблюдаемость

- Все ошибки сервера пишутся в лог с идентификатором запроса
- Подключается сбор ошибок прода: белый экран у гостя должен становиться известным сразу, а не через месяц от заказчика
- Гость никогда не видит технический текст ошибки, только понятное сообщение и предложение позвонить
- Ошибки внешних систем не приводят к ошибке для гостя
- В разделе «Система и безопасность» видно: статус последней резервной копии, число заявок в статусе failed, последние события безопасности
- Счётчик аналитики подключается только после согласия на cookie

## 12. Целостность данных

- Все операции, затрагивающие несколько таблиц, выполняются в транзакции
- Удаление сущности с привязанными медиа удаляет и медиа
- Скрытие сущности не удаляет связи
- Закреплённая статья ровно одна: закрепление новой снимает прежнюю в той же транзакции
- Занятие нельзя удалить, если оно стоит в расписании: сначала предупреждение
- Порядок сортировки пересчитывается атомарно при перетаскивании

## 13. Адреса и редиректы

- Slug генерируется из названия транслитерацией, проверяется на уникальность
- При смене slug старое значение сохраняется в таблице редиректов
- Промежуточный обработчик отвечает постоянным редиректом со старого адреса на новый
- `sitemap.xml` собирается из опубликованных сущностей, обновляется при публикации
- Черновики и скрытые сущности отдают `noindex` и в карту сайта не попадают

## 13a. Журнал заявок и персональные данные

Журнал это страховка на случай недоступности amoCRM, а не хранилище персональных данных.

- В файл журнала телефон пишется маскированным: `+7 916 ХХХ 41-77`
- Полный телефон и имя хранятся только в базе в зашифрованном виде
- Расшифровка происходит в панели и в выгрузке, обе операции пишутся в журнал действий
- Файл журнала лежит в томе с правами только для приложения

Иначе шифрование в базе теряет смысл: открытый файл рядом сводит его на нет.

## 14. Демонстрационные и настоящие данные

- `prisma/seed.ts` заполняет базу примерами для разработки
- Настоящие материалы студии загружаются через панель, а не скриптом
- Перед приёмкой демонстрационные данные удаляются или явно помечаются
- Настоящие телефоны гостей не попадают в тестовые данные, в скриншоты и в репозиторий
