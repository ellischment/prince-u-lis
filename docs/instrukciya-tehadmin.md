# Инструкция для технического администратора

Для роли **«Технический доступ»** (`tech`) и для того, кто держит сервер. В панели видит всё, включая разделы владельца.

Смежные документы: `DEPLOY.md` (выкатка и стадии), `ARCHITECTURE.md` (кэш, действия, фоновые задачи), `SPEC.md` (состав работ), `integracii-amocrm-telegram.md` (ключи amoCRM и Telegram).

---

## 1. Доступ к серверу

```bash
ssh -i ~/.ssh/princ_deploy_ed25519 root@СЕРВЕР
```

- Вход **только по ключу**, пароль отключён. Пользователи: `root` и `deploy`.
- Проект: `/root/app`. Секреты: `/root/app/.env`, права `600`, **в репозитории их нет и быть не должно**.
- Тестовый адрес закрыт паролем браузера (`basic_auth`, логин `studia`) и запретом индексации.

> **Не отключайте вход root**, пока у пользователя `deploy` команда `sudo` требует пароль, которого никто не знает. Иначе доступ к серверу будет потерян. Сначала настройте `deploy` беспарольный sudo, потом закрывайте root.

## 2. Ежедневное обслуживание

| Что | Команда |
|---|---|
| Состояние | `cd /root/app && docker compose ps` |
| Логи приложения | `docker compose logs -f app` |
| Перезапуск | `docker compose restart app` |
| Место на диске | `df -h /` |

Работают три задания по расписанию (`crontab -l` у root):

- **04:00** резервная копия базы и загруженных файлов;
- **каждые 5 минут** повтор неудачных заявок;
- **воскресенье 04:30** чистка осиротевших файлов медиа.

Ключ `CRON_SECRET` в crontab не записан: команда берёт его из окружения контейнера, поэтому в файле расписания секрета нет.

## 3. Выкатка обновлений

```bash
cd /root/app && sh scripts/deploy.sh
```

Скрипт снимает копию базы, запоминает текущую версию для отката, обновляет код, пересобирает и ждёт готовности. Откат: `sh scripts/rollback.sh`.

**Перед выкаткой сохраните `Caddyfile`.** На сервере он заменён тестовым (нужный домен плюс пароль), в репозитории лежит другой. Обычный `git pull` его не трогает, но `git checkout Caddyfile` сотрёт пароль.

```bash
cp /root/app/Caddyfile /root/Caddyfile.test.bak
```

## 4. Резервные копии и восстановление

Копии лежат в томе `backups` внутри контейнера: `/app/backups`.

```bash
# сделать копию прямо сейчас
docker compose exec -T app sh /app/scripts/backup.sh

# проверить, что копия рабочая (делайте раз в месяц)
docker compose exec -T app sh /app/scripts/restore-check.sh

# посмотреть список копий
docker compose exec -T app ls -la /app/backups/
```

Копия снимается через `sqlite3 .backup`, а не копированием файла: копия живой базы обычным `cp` получается битой. Восстановление проверено на практике, занимает меньше секунды.

## 5. Пароли панели

**Пароль панели живёт в базе в виде хэша.** Файл `.env` читает только скрипт первичного заполнения. Правка `.env` сама по себе пароль не меняет.

```bash
# посмотреть почту и пароль владельца, заданные при установке
grep -E '^SEED_(OWNER|ADMIN)_(EMAIL|PASSWORD)' /root/app/.env
```

Правильный порядок смены пароля: войти в панель, раздел **«Настройки и доступы»**, сменить там, затем вписать то же значение в `.env`, чтобы файл и база не разошлись. Минимальная длина 10 символов.

> **Никогда не запускайте скрипт первичного заполнения (`seed`) на боевом или тестовом сервере ради смены пароля.** Он зальёт демонстрационные данные поверх настоящего наполнения студии.

**Снять блокировку входа** (5 неудачных попыток закрывают адрес на час):

```bash
cd /root/app && docker compose exec -T app sqlite3 /app/prisma/data/dev.db 'DELETE FROM LoginAttempt WHERE success = 0;'
```

## 6. Наполнение сайта из таблицы

Первичное заполнение делается один раз, дальше студия правит всё в панели.

```bash
# 1. Таблица в JSON (на машине разработчика)
python scripts/content/normalize.py "Таблица.xlsx" prisma/content/lessons.json

# 2. Фото на сервер: паковать в архив, иначе кириллические имена бьются
tar -czf photos.tar.gz -C "папка с фото" .
scp -i ~/.ssh/princ_deploy_ed25519 photos.tar.gz root@СЕРВЕР:/root/
ssh ... "mkdir -p /root/photos && tar -xzf /root/photos.tar.gz -C /root/photos"

# 3. Импорт внутри контейнера
docker compose cp /root/photos app:/tmp/photos
docker compose exec -T app node node_modules/.bin/tsx prisma/import-content.ts /tmp/photos

# 4. ОБЯЗАТЕЛЬНО сбросить кэш, иначе сайт покажет старое
docker compose exec -T app rm -rf /app/.next/cache
docker compose restart app
```

Импорт пересоздаёт наполнение и **не трогает** пользователей панели.

## 7. Известные грабли

Всё это уже проявлялось. Не тратьте время на поиск заново.

**«Приложение не ответило за 60с» при выкатке, хотя сайт работает.**
Исправлено. Причина была двойная: Next слушал адрес контейнера вместо `0.0.0.0`, а проверка готовности ходила на `localhost`, который внутри контейнера уходит в IPv6. Теперь в `docker-compose.yml` задан `HOSTNAME: 0.0.0.0`, а проверка обращается к `127.0.0.1`.

**Ошибка 500 при входе в панель сразу после выкатки.**
Вкладка осталась от старой сборки и отправляет форму на серверное действие, которого больше нет. Лечится обновлением страницы (Ctrl+Shift+R). Пользователю теперь показывается понятный экран «Страница устарела», а не общая ошибка.

**Смена пароля `basic_auth` не применяется.**
`caddy reload` рапортует успех, но пароль не меняет. Нужен полный перезапуск:

```bash
docker compose exec -T caddy caddy hash-password --plaintext 'НОВЫЙ'   # получить хэш
# заменить хэш в строке studia в /root/app/Caddyfile
docker compose restart caddy
```

**Правки в базе мимо панели не видны на сайте.**
Панель сбрасывает кэш сама, любое её действие заканчивается сбросом. А скрипты, пишущие в базу напрямую, этого не делают: после них чистите `/app/.next/cache` и перезапускайте контейнер.

**`docker compose exec` внутри скрипта съедает остаток скрипта.**
Добавляйте `</dev/null` к каждому такому вызову, иначе команда заберёт стандартный ввод и следующие строки не выполнятся.

**Копирование файлов с кириллицей через `scp` теряет файлы.**
Паковать в `tar.gz` и распаковывать на сервере.

## 8. Безопасность: что уже сделано

- HTTPS от Let's Encrypt, продлевается сам. Обращение по HTTP перебрасывается на HTTPS. Оценка SSL Labs **A**.
- Заголовки: `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`.
- OWASP ZAP в базовом режиме: **ни одной ошибки**, остальные замечания разобраны в `STATE.md`.
- Вход по SSH только по ключу, включён `ufw` (22, 80, 443), работает `fail2ban`, включены автоматические обновления безопасности.
- Телефоны и имена в базе зашифрованы, в журнале телефон маскируется.
- Загрузка файлов проверяется по содержимому, лимит 10 МБ на файл и 12 МБ на запрос в Caddy.
- Не более 5 заявок с одного адреса за 10 минут, дальше отказ.

**Что осталось до боевого домена:** проверка на `securityheaders.com` (сейчас мешает пароль тестового сайта), живые сценарии из `DEPLOY.md` разделы B3 и B4, контрольная заявка в тестовую воронку amoCRM.

## 9. Быстрая диагностика «сайт не работает»

```bash
cd /root/app
docker compose ps                      # оба контейнера должны быть Up
docker compose logs --tail=50 app      # ошибки приложения
curl -s -o /dev/null -w '%{http_code}\n' -u 'studia:ПАРОЛЬ' https://АДРЕС/
df -h /                                # не кончилось ли место
```

Если контейнер падает: `docker compose logs app` покажет причину. Если место кончилось, чистите старые копии в `/app/backups` и образы `docker image prune -a`.
