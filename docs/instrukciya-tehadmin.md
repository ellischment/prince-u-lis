# Инструкция для технического администратора

Для роли `tech` и того, кто держит сервер. В панели видит всё. Смежные
документы: `DEPLOY.md`, `ARCHITECTURE.md`, `plan-vykatki.md`,
`integracii-amocrm-telegram.md`.

Стек: Next.js + Prisma + SQLite + Docker + Caddy. Проект на сервере: `/root/app`.

---

## 1. Доступ к серверу

```bash
ssh -i ~/.ssh/princ_deploy_ed25519 root@СЕРВЕР
```

- Вход только по ключу, пароль отключён.
- Секреты: `/root/app/.env` (права 600). В репозитории их нет.
- Тестовый домен закрыт паролем браузера (basic_auth, логин `studia`) и
  запретом индексации (`NEXT_PUBLIC_NOINDEX=1`). Боевой — без этого.

---

## 2. Ежедневное обслуживание

```bash
cd /root/app
docker compose ps            # живы ли контейнеры
docker compose logs -f app   # логи приложения
df -h /                      # место на диске
free -m                      # память
```

Cron у root (`crontab -l`): бэкап 04:00, повтор заявок каждые 5 минут, чистка
медиа вс 04:30, чистка кэша сборки Docker вс 05:00. `CRON_SECRET` берётся из
окружения контейнера, в crontab его нет.

---

## 3. Выкатка обновлений

```bash
cd /root/app && sh scripts/deploy.sh
```

Скрипт: копия базы → запоминает версию для отката → `git pull` → пересборка →
ожидание готовности. Откат: `sh scripts/rollback.sh`.

**Грабля памяти (важно).** На сервере 2 ГБ; `next build` во время выкатки
прожорлив и может оборвать SSH-сессию — сборка прервётся на середине, контейнеры
останутся старыми. Поэтому запускайте выкатку отвязанно от сессии:

```bash
cd /root/app && nohup sh scripts/deploy.sh > /root/deploy-bg.log 2>&1 &
# следить: tail -f /root/deploy-bg.log  (ждём строку «Готово. Выкачено»)
```

**Конфиг Caddy.** В репозитории два файла: `Caddyfile` (боевой домен) и
`Caddyfile.test` (тестовый: свой адрес и пароль). Какой взять — задаёт
`CADDYFILE` в `.env`; адрес и хэш пароля теста тоже в `.env`
(`TEST_DOMAIN`, `TEST_AUTH_USER`, `TEST_AUTH_HASH`). Поэтому `git pull` больше
ничего не затирает, руками сохранять Caddyfile не нужно. Хэш пароля в `.env`
пишется с УДВОЕННЫМИ `$` (`$$2a$$14$$...`), иначе docker compose съест `$` и
пароль приедет обрезанным.

## 4. Заглушка на время работ

Отдаётся самим Caddy, работает даже при остановленном приложении.

```bash
cd /root/app
sh scripts/maintenance-on.sh    # включить: сайт отвечает 503 + страница с телефоном
sh scripts/maintenance-off.sh   # выключить: сайт снова открыт
```

Включайте перед долгими работами. Проверка: `curl -sI https://ДОМЕН/ | head -1`
(ждём 503 при включённой, 200 при выключенной).

## 5. Резервные копии и восстановление

```bash
# копия сейчас
docker compose exec -T app sh /app/scripts/backup.sh
# список копий
docker compose exec -T app sh -c 'ls -la /app/backups' </dev/null
# проверка целостности базы
docker compose exec -T app sqlite3 /app/prisma/data/dev.db 'PRAGMA integrity_check;' </dev/null
```

Восстановление из копии описано в `DEPLOY.md`. Восстанавливать под остановленным
приложением, не под работающим.

---

## 6. ГЛАВНАЯ ГРАБЛЯ: кэш после правок мимо панели

Любая правка данных В ОБХОД панели (прямой SQL, `import:content`, сид) НЕ
сбрасывает кэш чтения — ни `restart`, ни пересборка не помогают, потому что
`.next/cache` переживает их. Сайт будет показывать старое, хотя в базе уже новое.

После любого такого вмешательства обязательно:

```bash
cd /root/app
docker compose exec -T app sh -c 'rm -rf /app/.next/cache' </dev/null
docker compose restart app
```

Правки через панель этим не болеют — там кэш сбрасывается сам. Команды в
ssh-heredoc всегда с `</dev/null` в конце, иначе `docker compose exec` съедает
ввод и виснет.

## 7. Пароли панели и роли

Пароли сидов берутся из `.env` (`SEED_*_PASSWORD`). Смена пароля/роли —
владельцем в панели «Настройки и доступы». Роли: `owner` (всё), `admin`
(содержимое без «Настройки/Журнал/Система»), `tech` (всё). Мастера НЕ связаны
с пользователями — это карточки, не аккаунты.

После пяти неверных входов адрес блокируется на час (`LoginAttempt`).

---

## 8. Быстрая диагностика «сайт не работает»

1. `docker compose ps` — оба контейнера Up? Если app перезапускается —
   `docker compose logs app --tail=50`, искать ошибку.
2. `df -h /` — не кончилось ли место (кэш сборки Docker растёт; чистит
   недельный cron, вручную `docker builder prune -f`).
3. `free -m` — не ушло ли в своп при сборке.
4. Заявки не уходят в amoCRM — проверить ключ: `npm run amo:probe` локально;
   заявки при этом не теряются, лежат в базе со статусом `failed` и уходят
   повтором.
5. Ничего не помогло — откат: `sh scripts/rollback.sh`.

---

## 9. Безопасность (проверить на боевом сервере)

Вход по SSH только по ключу, root по SSH закрыт, работа под `deploy` с sudo,
`ufw` открыт только на 22/80/443, `fail2ban` на SSH, автообновления
безопасности. Заголовки (CSP, HSTS и т.д.) ставит приложение в `next.config.ts`.
TLS — Let's Encrypt через Caddy, продлевается сам.
