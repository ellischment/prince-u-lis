# CLAUDE.md. Правила работы над проектом

Этот файл агент читает автоматически при каждом запуске. Не удалять и не переименовывать.

## Что это за проект

Сайт студии «Принц и Лис» с онлайн-записью и панелью управления. Полная спецификация в `SPEC.md`. Текущее состояние работ в `STATE.md`. План этапов в `PLAN.md`.

## Обязательный порядок действий в начале каждой задачи

1. Прочитать `SPEC.md` целиком.
2. Для задач с базой, панелью, кэшем или заявками прочитать `ARCHITECTURE.md`.
3. Перед реализацией любой функции прочитать её раздел в `FEATURES.md`: там логика, крайние случаи и способ проверки.
4. Прочитать `STATE.md` и понять, на каком шаге проект.
5. Если задача не соответствует текущему шагу в `STATE.md`, сказать об этом и спросить, прежде чем что-то менять.
6. Проверить `git status`. Если есть незакоммиченные изменения, сначала разобраться с ними.

## Обязательный порядок в конце каждой задачи

1. Запустить `npm run check` (типы, линтер, сборка, тесты). Не заканчивать работу с падающей проверкой.
2. Обновить `STATE.md`: что сделано, что дальше, какие вопросы открыты.
3. Сделать коммит с понятным сообщением на русском.
4. Коротко отчитаться: что сделано, что проверено, что осталось.

## Развёртывание

Порядок выкатки, проверка безопасности и перенос на боевой домен описаны в `DEPLOY.md`. Тестовый домен закрыт паролем и запретом индексации, боевой открывается только после прохождения стадии B.

## Заготовки

В папке `starter/` лежат готовые файлы: схема базы, клиент, кэш, обёртка серверных действий, конвейер заявки, контейнер, тесты. Использовать их, а не писать заново. В них уже учтены грабли из `TECH-REVIEW.md`.

## Стек

Next.js (App Router) + TypeScript + Prisma + SQLite. Стили обычным CSS без UI-китов. sharp для изображений. Никаких новых зависимостей без явного разрешения.

## Единственные источники правды

Если два файла говорят разное, побеждает источник из этой таблицы. Расхождение это ошибка, о ней надо сказать, а не выбирать самому.

| Что | Где | Комментарий |
|---|---|---|
| Палитра, шрифты, скругления | `SPEC.md` раздел 12 и `DESIGN-LOCK.md` | `globals.css` повторяет их один в один; макет `4-2-2` — истина композиции |
| Модель данных | `SPEC.md` раздел 2 и `prisma/schema.prisma` | При расхождении сначала спросить |
| Логика функции | `FEATURES.md` | Крайние случаи там же |
| Кэш и серверные действия | `ARCHITECTURE.md` раздел 3 и 7 | |
| Разметка для поиска | `SEO.md` | |
| Состав работ и приёмка | `SPEC.md` | Это приложение к договору, менять нельзя |

## Правила кода

- TypeScript строгий, `any` запрещён.
- Серверная валидация обязательна для всех форм. Клиентская валидация не заменяет серверную.
- Все тексты интерфейса на русском, без длинных тире.
- Никаких секретов в коде: только переменные окружения. `.env` в `.gitignore`.
- Изображения через `next/image`, ленивая загрузка.
- Любой обработчик формы пишет в базу до обращения к внешним сервисам.
- Любое серверное действие панели заканчивается сбросом кэша по карте `ARCHITECTURE.md` раздел 3. Действие без сброса считается незавершённым.
- Крайние случаи из `FEATURES.md` обрабатываются, а не игнорируются. Если случай не описан, спросить.
- Разметка schema.org делается по `SEO.md`. Поле, которое нечем заполнить, не выводится: выдуманные значения приводят к санкциям поисковика.
- Проверка роли выполняется на сервере в каждом действии, а не только скрытием пунктов меню.
- Сырой SQL запрещён, кроме `PRAGMA` при инициализации.
- Внешние вызовы (amoCRM, Telegram) с таймаутом и обработкой ошибки. Падение внешнего сервиса не должно ронять заявку.
- Любая правка стиля или вёрстки требует ДО починки: diff рендера против макета `4-2-2` на трёх ширинах (320/390/1440) и таблицы расхождений (страница, элемент, ширина, что не так, причина, канон из макета). Чинить только к значениям из `DESIGN-LOCK.md`. Цвет — только `var(--*)` (сырой hex лишь в токен-файлах). Осознанные отступления выносить отдельным списком, не выдавать за баги.

## Правила по продукту

Эти вещи нарушать нельзя, они согласованы с заказчиком:

- Количество мест нигде не считается и не хранится.
- В панели нет списка клиентов, подтверждения, переноса и отмены записи. Это amoCRM.
- Telegram-бот односторонний: только отправка, никаких кнопок и вебхуков.
- Видео не хранится на сервере, только ссылки на VK Видео, Rutube, YouTube.
- Фото и видео гостей публикуются только при отметке о письменном согласии.
- Ссылки на сервисы Meta на сайт не добавляются.
- На каждой странице ровно один H1.
- Гирлянда не привязана к курсору.
- Аналитика включается только после согласия на cookie.

## Definition of Done для любой задачи

- [ ] Работает на ширине 320px без горизонтальной прокрутки
- [ ] Низ страницы чистый: прокручено до конца, под подвалом нет посторонних блоков и значков (`DESIGN-LOCK.md`, «Проверка низа страницы»)
- [ ] Работает с клавиатуры, фокус виден
- [ ] Серверная валидация есть
- [ ] Ошибки обрабатываются, пользователь видит понятное сообщение
- [ ] `npm run check` проходит, включая тесты
- [ ] Изменение выкачено и проверено на боевом адресе
- [ ] Соответствующий раздел панели работает и меняет сайт: пройден чек-лист `ARCHITECTURE.md` раздел 15
- [ ] `STATE.md` обновлён

## Чего не делать без спроса

- Менять модель данных, описанную в `SPEC.md`
- Добавлять библиотеки
- Менять палитру, шрифты и композицию
- Трогать код этапов, которые уже приняты, если задача про другое
- Делать «заодно» рефакторинг соседнего кода

## Как отвечать

Коротко, по делу, на русском. Если что-то в спецификации противоречиво или непонятно, спросить, а не догадываться. Если задача выглядит слишком большой для одного шага, предложить разбить.
