# DEPLOY. Развёртывание: тестовый домен, проверка безопасности, боевой запуск

Три стадии. Тестовый домен нужен, чтобы ошибки и проверки безопасности не происходили на глазах у гостей студии.

```
Ноутбук  ->  Тестовый домен  ->  Боевой домен
  0.1-0.5      шаг 0.6            этап 12
```

---

# Стадия A. Тестовый домен

## A1. Что покупать

| Что | Сколько | На кого |
|---|---|---|
| VPS в России, 2 ядра, 2 ГБ памяти, 20 ГБ диска | 500–900 руб/мес | на студию |
| Тестовый домен, например princ-test.ru | 200–400 руб/год | можно на себя |

Тестовый домен можно взять любой дешёвый в зоне ru или использовать поддомен основного, например `test.princulissart.ru`, если основной уже зарегистрирован. Второй вариант дешевле и проще.

Боевой домен `princulissart.ru` оформляется на студию по договору.

## A2. Подготовка сервера

Заходим по SSH и делаем базовую защиту до того, как поднимать приложение. Сервер, выставленный в интернет без этого, начинают перебирать в течение часа.

```bash
# 1. Обновление системы
apt update && apt upgrade -y

# 2. Отдельный пользователь вместо root
adduser deploy
usermod -aG sudo deploy

# 3. Вход по ключу вместо пароля
# На своём ноутбуке: ssh-keygen -t ed25519
# Затем скопировать ключ на сервер:
ssh-copy-id deploy@АДРЕС_СЕРВЕРА

# 4. Запретить вход по паролю и под root
sudo nano /etc/ssh/sshd_config
#   PasswordAuthentication no
#   PermitRootLogin no
sudo systemctl restart ssh

# 5. Файрвол: только нужные порты
sudo ufw allow OpenSSH
sudo ufw allow 80
sudo ufw allow 443
sudo ufw enable

# 6. Защита от перебора
sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban

# 7. Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker deploy
```

После пункта 4 обязательно проверьте вход в новом окне терминала, не закрывая текущее. Если что-то пошло не так, у вас останется рабочее соединение.

## A3. Первая выкатка

```bash
# На сервере
mkdir -p ~/app && cd ~/app
git clone АДРЕС_РЕПОЗИТОРИЯ .

cp starter/env.example .env
nano .env          # заполнить секреты, домен указать тестовый

docker compose up -d --build
docker compose logs -f app
```

В `Caddyfile` на время тестов указывается тестовый домен. Сертификат Caddy получит сам за несколько секунд.

## A4. Закрыть тестовый сайт от посторонних

Это обязательно. Тестовый сайт с настоящими текстами студии, попавший в поисковую выдачу, потом годами всплывает в результатах и мешает основному.

Три меры сразу:

**1. Пароль на весь сайт.** В `Caddyfile` для тестового домена:

```
test.princulissart.ru {
	basic_auth {
		studia $2a$14$ХЭШ_ПАРОЛЯ
	}
	reverse_proxy app:3000
}
```

Хэш получается командой `caddy hash-password`.

**2. Запрет индексации.** Переменная `NEXT_PUBLIC_NOINDEX=1` в `.env` тестового сервера. Приложение при ней отдаёт заголовок `X-Robots-Tag: noindex` и `robots.txt` с полным запретом.

**3. Тестовые интеграции.** На тестовом сервере amoCRM и Telegram работают в отдельную воронку и отдельный чат, чтобы тестовые заявки не смешивались с настоящими.

# Стадия B. Проверка безопасности

Проводится на тестовом домене, до переноса на боевой. Каждый пункт отмечается галочкой в этом файле.

## B1. Транспорт и заголовки

- [ ] Сайт открывается только по HTTPS, обращение по HTTP перебрасывает на HTTPS
- [ ] Оценка на `ssllabs.com/ssltest` не ниже A
- [ ] Оценка на `securityheaders.com` не ниже A
- [ ] Заголовки отдаются: `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Content-Security-Policy`
- [ ] Сертификат обновляется автоматически, проверено датой окончания

## B2. Сервер

- [ ] Вход по SSH только по ключу, пароль отключён
- [ ] Вход под root запрещён
- [ ] Открыты только порты 22, 80, 443: проверить `sudo ufw status`
- [ ] fail2ban работает: `sudo fail2ban-client status sshd`
- [ ] Автоматические обновления безопасности включены
- [ ] Порт базы наружу не смотрит: у нас SQLite, порта нет вообще

## B3. Приложение

- [ ] Панель `/admin` недоступна без входа, проверено в режиме инкогнито
- [ ] Прямое обращение к серверным действиям без сессии отклоняется
- [ ] Роль `admin` не может выполнить действие владельца прямым запросом
- [ ] После 5 неудачных входов адрес блокируется на час
- [ ] Сессия истекает, после истечения панель требует вход заново
- [ ] Смена роли пользователя завершает его текущие сессии

## B4. Формы и данные

- [ ] Заявка без согласия не принимается на сервере, а не только в браузере
- [ ] Более 5 заявок с одного адреса за 10 минут отклоняются
- [ ] Отправка заведомо мусорных данных не роняет приложение
- [ ] Попытка вставить исполняемый код в комментарий и в статью не приводит к его выполнению
- [ ] Загрузка файла с подменённым расширением отклоняется
- [ ] Файл больше 10 МБ отклоняется и приложением, и прокси
- [ ] Телефоны в базе зашифрованы: проверить прямым запросом к файлу базы
- [ ] В текстовом журнале телефон маскирован
- [ ] Публикация фото или видео отзыва без отметки согласия невозможна

## B5. Секреты

- [ ] `.env` отсутствует в репозитории: `git log --all -- .env` пусто
- [ ] В истории нет токенов: `git log -p | grep -iE "token|secret|password"` без находок
- [ ] Пароль владельца не совпадает с тем, что был в примерах
- [ ] Секреты на тестовом и боевом серверах разные
- [ ] Права на файл базы и `.env`: только владелец процесса

## B6. Зависимости

- [ ] `npm audit` без критических и высоких уязвимостей
- [ ] Версии зафиксированы через `package-lock.json`
- [ ] Обновление зависимостей запланировано раз в квартал

## B7. Восстановление

- [ ] Резервная копия создаётся по расписанию, файлы на месте
- [ ] Копия сделана через `sqlite3 .backup`, а не копированием
- [ ] **Восстановление проверено на практике**: развернуть копию в отдельный файл, запустить приложение на ней, убедиться что данные целы
- [ ] Известно, сколько времени занимает восстановление

Пункт про практическую проверку восстановления главный во всём списке. Резервная копия, которую ни разу не разворачивали, это не копия, а надежда.

## B8. Инструменты проверки

| Что | Чем |
|---|---|
| Заголовки | securityheaders.com |
| Сертификат | ssllabs.com/ssltest |
| Типовые уязвимости | OWASP ZAP, режим baseline |
| Зависимости | `npm audit` |
| Скорость и доступность | Lighthouse во вкладке разработчика |
| Доступность | расширение axe DevTools |

ZAP запускается одной командой в контейнере и даёт отчёт за несколько минут:

```bash
docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://test.princulissart.ru -r zap-report.html
```

Часть замечаний будет ложными, разбирайте по одному, а не чините всё подряд.

# Стадия C. Перенос на боевой домен

## C1. Перед переносом

- [ ] Все пункты стадии B пройдены
- [ ] Приёмка по `SPEC.md` раздел 20 пройдена
- [ ] Настоящие материалы студии загружены, демонстрационные удалены
- [ ] Домен `princulissart.ru` оформлен на студию и делегирован на сервер
- [ ] Токены amoCRM и Telegram боевые, не тестовые
- [ ] Резервная копия сделана и проверена

## C1a. Где лежат данные и как они переезжают

Наполнение сайта это **две вещи**, и обе намеренно не в репозитории (`.gitignore`:
содержимое студии, а не код):

| Что | Локально | На сервере |
|---|---|---|
| База: занятия, мастера, цены, тексты, заявки | один файл `prisma/data/dev.db` | том `db-data` → `/app/prisma/data` |
| Загруженные фотографии | папка `public/uploads` | том `uploads` → `/app/public/uploads` |

База это SQLite: отдельного сервера базы нет, всё в одном файле. Панель пишет
прямо в него, поэтому «перенести сайт» = перенести файл базы и папку фото.

**Заново заливать наполнение из Excel не нужно.** `npm run import:content` это
разовая операция первичного наполнения; после неё студия правит всё в панели, и
правки живут в базе. Повторный импорт, наоборот, затрёт правки, сделанные в
панели, — запускать его после переезда не нужно.

```bash
# Снять снимок данных с рабочей машины (приложение остановлено)
npm run data:snapshot          # -> backups/<дата>/ : dev.db + uploads

# Развернуть снимок обратно (на другой машине или после сбоя)
npm run data:snapshot -- restore backups/<дата>

# Убрать файлы, на которые больше нет ссылок в базе
npm run media:prune            # отчёт
npm run media:prune -- --yes   # удалить
```

Копию перед переездом снимать обязательно, и обязательно проверять
разворачиванием: копия, которую ни разу не разворачивали, это не копия.

## C2. Перенос

```bash
# 0. Наполнение на сервер: снимок с рабочей машины в тома контейнера
#    (db-data и uploads). Делается один раз, до первого запуска.
npm run data:snapshot
docker compose cp backups/<дата>/dev.db app:/app/prisma/data/dev.db
docker compose cp backups/<дата>/uploads/. app:/app/public/uploads/

# 1. Копия текущего состояния
sh scripts/backup.sh

# 2. Домен в Caddyfile меняется на боевой, basic_auth убирается
nano Caddyfile

# 3. NEXT_PUBLIC_NOINDEX убирается из .env
nano .env

# 4. Выкатка
docker compose up -d --build

# 5. Проверка
curl -I https://princulissart.ru
```

## C3. Сразу после переноса

- [ ] Сайт открывается по обоим адресам: с www и без
- [ ] `robots.txt` разрешает индексацию, `sitemap.xml` отдаётся
- [ ] Тестовая заявка доходит до боевой воронки amoCRM и в боевой чат
- [ ] Счётчик статистики работает и подключается только после согласия
- [ ] Тестовая заявка удалена из amoCRM
- [ ] Тестовый домен выключен или оставлен закрытым паролем

## C4. Откат

Если что-то пошло не так:

```bash
git checkout ПРЕДЫДУЩАЯ_МЕТКА
docker compose up -d --build
```

База при этом не трогается. Если проблема в данных, разворачивается копия из `backups`.

Откат должен быть отрепетирован до боевого запуска, а не изучаться в момент аварии.

# Что делать, если сервера ещё нет

Шаги с 0.1 по 0.5 полностью выполняются на ноутбуке, это примерно неделя работы. Если к шагу 0.6 сервер не появился, есть два пути.

**Первый.** Взять любой VPS на себя на месяц, поднять тестовый домен там, продолжать по плану. Перенос на сервер студии потом займёт полдня: тот же `docker compose up`.

**Второй.** Сдвинуть шаг 0.6 и идти дальше по плану. Но тогда возвращается риск, ради которого шаг и придуман: всё окружение вылезет разом в конце, и это худший момент для сюрпризов.

Рекомендую первый. Стоимость месяца VPS несопоставима с неделей отладки в конце.
